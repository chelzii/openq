# OpenQ 项目最终版实现文档

## 1. 文档定位

本文件严格以 [最终版需求文档.md](/home/chelizi/project/openq/docs/xuqiu/最终版需求文档.md) 为依据，只定义**最终交付时系统必须长成什么样**。

本文件回答四个问题：

1. 最终系统由哪些模块组成。
2. 每个模块具体怎么实现。
3. 每个模块做到什么程度算交付。
4. 哪些内容属于课题边界内，哪些内容明确不做。

## 2. 最终实现目标

最终需要落地的是一套统一系统，而不是三个分散原型：

**OpenClaw + 统一调用网关 + 虚拟 App 生态 + 第一层动态意图护栏 + 第二层 FISCO BCOS 验签验权 + 简易沙箱 + 文件/记忆完整性检测 + 网站演示端 + 实验与审计模块**

这套系统必须同时满足：

1. 能支撑老师要求的最终演示。
2. 能支撑论文第五章“系统实现”。
3. 能支撑论文第六章“实验设计与结果分析”。
4. 能统一承载三类攻击实验和三种防护模式对比。

## 3. 最终系统总览

## 3.1 总体结构

最终系统固定为下面 8 个组成部分：

1. `OpenClaw` 接入层
2. 统一调用网关
3. 虚拟 App 层
4. 第一层动态意图护栏
5. 第二层 `FISCO BCOS` 身份与权限验证层
6. 简易沙箱/受控执行层
7. 文件与记忆完整性检测、审计与存证层
8. 网站演示端

## 3.2 最终请求链路

最终一次完整请求必须按下面链路运行：

1. 用户在网站演示端输入任务。
2. `OpenClaw` 理解任务，并生成结构化工具调用意图。
3. 调用进入统一网关。
4. 第一层动态意图护栏做输入拆分、信任分区、意图一致性判断。
5. 高风险请求进入第二层 `FISCO BCOS` 验签与验权。
6. 通过校验后，调用进入简易沙箱中的虚拟 App。
7. 执行结果、本地审计日志、链上摘要同步记录。
8. 页面展示回复内容、拦截原因、执行结果和审计信息。

这个链路必须能在三种模式下运行：

1. `off`
2. `guard_only`
3. `full`

## 3.3 固定运行模式定义

为了避免实现过程中对三种模式理解不一致，最终模式定义固定如下：

### 1. `off`

- 不启用第一层动态意图护栏
- 不启用第二层 `FISCO BCOS` 验签验权
- 不启用受保护状态写入审批
- 仅保留基础执行记录，作为对照组

### 2. `guard_only`

- 启用第一层动态意图护栏
- 不启用第二层 `FISCO BCOS` 验签验权
- 受保护状态修改只做本地完整性检测、告警和必要回滚
- 用于体现单层认知防护效果

### 3. `full`

- 启用第一层动态意图护栏
- 启用第二层 `FISCO BCOS` 验签验权
- 启用受保护状态写入审批、回滚和链上摘要存证
- 用于体现最终完整方案

## 3.4 固定执行协议

依据需求文档和 PDF 约束，最终系统的执行协议固定为：

1. `OpenClaw` 只生成结构化调用意图，不直接执行底层动作。
2. 所有动作统一抽象成 `call_app_api` 协议，不允许自由文本命令直达执行层。
3. 调用负载在进入网关前必须带请求摘要、调用实体标识、签名信息和上下文摘要。
4. 网关先做结构校验，再做第一层风险判断，再做第二层验签验权，最后才允许执行。
5. 执行后必须返回结构化结果，并同步生成本地审计记录与链上摘要。
6. 对共享提示词、长期记忆、关键配置的修改，也视为受保护动作，必须纳入同一协议，而不是绕过网关直接改文件。

这意味着最终系统不能存在两套执行逻辑：

1. 一套 App 调用走网关
2. 一套状态写入直接改文件

最终必须统一成一套受控调用协议。

## 3.5 推荐最终工程结构

为了避免三个原型继续并行漂移，最终工程建议收敛成单一主工程，目录边界固定如下：

```text
openq/
  app/
    api/
    core/
    guards/
    chain/
    apps/
    state/
    audit/
    demo/
    schemas/
  data/
    fixtures/
    experiments/
    baselines/
  scripts/
  docs/xuqiu/
  prototypes/
```

建议职责如下：

1. `api/`
   网关与页面路由
2. `core/`
   OpenClaw 接入、模式调度、统一编排
3. `guards/`
   第一层动态意图护栏
4. `chain/`
   `FISCO BCOS` 交互、DID、签名、验签、验权
5. `apps/`
   `Mail_App`、`Bank_App`、`Gallery_App`、`Weather_App`
6. `state/`
   共享提示词、记忆、关键配置的受保护状态管理
7. `audit/`
   本地日志和链上摘要存证
8. `demo/`
   演示页模板和展示逻辑
9. `schemas/`
   所有请求、响应、审计、实验数据结构

最终原则是：

- 不再把 `multiple-Agent`、`memory-p`、`supply-chain` 作为长期并行主目录继续开发
- 它们只作为迁移来源或参考材料
- 最终可交付系统必须收敛到单一主工程

## 4. 模块级详细实现方案

## 4.1 OpenClaw 接入层

### 目标

负责接入真实 `OpenClaw`，向其发送消息，接收结构化回复，并把回复引导到统一网关。

### 具体实现方案

1. 复用 [openclaw_client.py](/home/chelizi/project/openq/prototypes/multiple-Agent/openclaw_client.py) 的 WebSocket 接入能力。
2. 保留其设备签名、会话维持、消息发送、历史轮询逻辑。
3. 将现有“投资分析场景”的消息包装替换为“虚拟终端多 App 调用场景”。
4. 在最终系统中，`OpenClaw` 不直接操作底层 App，而是只能通过统一网关暴露的 `call_app_api` 入口访问能力。
5. `OpenClaw` 的 WebSocket 连接身份与系统调用身份分离管理：
   `OpenClaw` 设备配对身份只用于建立会话；
   网关调用身份使用独立的 `DID + signing keypair`。

### 边界

1. 不改造 `OpenClaw` 内核。
2. 不开发新的大模型能力。
3. 不把 `OpenClaw` 作为论文里的防御机制本身，它只是被保护对象和智能调度入口。

### 交付标准

做到下面三点即视为交付：

1. 能稳定连接 `OpenClaw`。
2. 能把用户任务转化为对网关的结构化调用。
3. 能在网页端展示 `OpenClaw` 的回复和调用结果。

## 4.2 统一调用网关

### 目标

统一承接所有跨 App 调用，作为第一层防御、第二层验证、沙箱执行和审计记录的唯一入口。

### 具体实现方案

建议使用：

1. `FastAPI`
2. `Pydantic`
3. `httpx`

建议固定一条核心调用接口：

```json
POST /api/call_app
{
  "request_id": "req-001",
  "session_id": "demo-001",
  "mode": "full",
  "did": "did:openq:agent-001",
  "resource_type": "app",
  "app": "bank",
  "action": "transfer",
  "args": {
    "target_account": "alice",
    "amount": 100
  },
  "context": {
    "user_goal": "总结邮件",
    "trusted_system_goal": "summarize_mail",
    "source_summary": "邮件中包含转账诱导指令"
  },
  "payload_hash": "...",
  "signature": "..."
}
```

受保护状态修改统一复用同一协议，只是 `resource_type` 不同：

```json
POST /api/call_app
{
  "request_id": "req-002",
  "session_id": "demo-001",
  "mode": "full",
  "did": "did:openq:agent-001",
  "resource_type": "state",
  "app": "state",
  "action": "update_memory",
  "args": {
    "target": "memory/main.md",
    "change_summary": "append trusted contact"
  },
  "context": {
    "user_goal": "更新记忆",
    "trusted_system_goal": "update_memory"
  },
  "payload_hash": "...",
  "signature": "..."
}
```

网关必须负责：

1. 请求结构校验
2. 调用模式切换
3. 调用链追踪 ID 生成
4. 第一层意图护栏接入
5. 第二层验签验权接入
6. 沙箱分发执行
7. 审计日志记录
8. 对 `resource_type=state` 的受保护状态写入触发审批、回滚和完整性记录

### 边界

1. 所有 App 调用必须先过网关。
2. 不允许 `OpenClaw` 或页面直接绕过网关调用 App。
3. 网关不直接处理复杂业务逻辑，只做编排、验证和分发。
4. 网关既负责 App 动作，也负责受保护状态写入动作，不能拆成两套路由体系。

### 交付标准

1. 所有虚拟 App 都只能通过网关访问。
2. 网关能根据运行模式切换不同防护路径。
3. 网关能完整记录每次调用的输入、结果和拦截原因。
4. 网关能统一处理 `app` 与 `state` 两类动作。

## 4.3 虚拟 App 层

### 目标

模拟手机终端中的多 App 能力，作为论文实验载体。

### 具体实现方案

最终建议固定保留 3 个核心 App，1 个可选 App。

#### 1. `Mail_App`

职责：

- 提供邮件列表
- 提供邮件详情读取
- 作为恶意提示注入载体

建议动作：

1. `list_messages`
2. `read_message`

#### 2. `Bank_App`

职责：

- 提供账户查询
- 提供模拟转账
- 作为高风险动作代表

建议动作：

1. `get_balance`
2. `transfer`

#### 3. `Gallery_App`

职责：

- 提供相册或文件列表
- 提供敏感文件读取
- 作为隐私数据访问载体

建议动作：

1. `list_assets`
2. `read_asset`

#### 4. `Weather_App`

职责：

- 作为正常外部上下文来源
- 可承载第三方返回内容中的恶意诱导文本

建议动作：

1. `get_weather`
2. `get_alert`

### 边界

1. 虚拟 App 是后端模块，不是安卓原生 App。
2. 不需要做真实联网银行、真实邮件服务接入。
3. App 能力必须收敛为少量白名单动作，不能泛化成任意命令执行。

### 交付标准

1. 至少 `Mail_App`、`Bank_App`、`Gallery_App` 三个 App 可稳定运行。
2. 三个实验场景均能由这些 App 触发。
3. 每个 App 均通过统一结构化接口暴露能力。

## 4.4 第一层动态意图护栏

### 目标

在调用真正落地前，从语义层阻断提示注入、越权诱导和任务偏移。

### 具体实现方案

最终固定采用“结构化规则 + Embedding 一判 + Reranker 二判”方案。

必须包含四个能力：

1. **输入拆分**
   将系统提示、用户原始任务、外部 App 返回内容分开处理。
2. **信任分区**
   将系统指令设为高信任，用户任务设为中信任，外部内容设为低信任。
3. **高风险动作识别**
   对 `transfer`、`read_asset`、`update_memory`、`update_prompt` 等动作单独标记。
4. **意图一致性判断**
   若原始任务是“总结邮件”，而动作是“转账”或“读取相册”，则判为不一致并阻断。

### 模型选型定稿

1. 正式基线 Embedding 模型固定采用 `BAAI/bge-base-zh-v1.5`。
2. 选用该模型的原因是：本项目主要处理中文短文本意图，比起通用占位向量或仅英文优化模型，更适合本地离线部署、实验复现和答辩演示。
3. `BAAI/bge-m3` 保留为升级选项，仅在后续需要处理中英混合、多语言或更长上下文时启用，不作为本次默认实现。
4. 高风险动作与灰区样本的二次复核固定采用 `BAAI/bge-reranker-v2-m3`。
5. 当前仓库中的 hashing trick 仅能作为开发占位方案，不能视为最终正式实现。

其中，意图一致性检测算法固定按下面方式实现：

1. 将用户原始自然语言目标记为 `U`
2. 将当前规划生成的底层动作说明记为 `A`
3. 使用 `BAAI/bge-base-zh-v1.5` 分别编码，得到向量 `v_u` 与 `v_a`
4. 使用余弦相似度计算第一阶段语义一致性得分 `S_embed`：

```text
S_embed(v_u, v_a) = (v_u · v_a) / (||v_u|| * ||v_a||)
```

5. 当 `S_embed` 接近 `1` 时，说明当前动作与用户原始目标高度一致
6. 当 `S_embed` 显著低于阈值时，说明执行路径发生语义偏移，应触发阻断或升级审查
7. 若请求属于高风险动作，或 `S_embed` 落在灰区，则将 `(U, A)` 作为成对输入送入 `BAAI/bge-reranker-v2-m3`，得到第二阶段相关性得分 `S_rerank`
8. 结合规则层结果、`S_embed` 和 `S_rerank` 共同给出最终放行、阻断或升级审查结论

正式实现采用三段式判定机制：

1. 规则层先拦截明显越权动作和显式提示注入标记
2. Embedding 相似度层进一步量化“原始意图”和“当前动作”之间的偏差
3. Reranker 层只处理高风险或灰区样本，降低纯余弦相似度在短文本场景下的误报和漏报

建议输出字段至少包含：

```json
{
  "allowed": false,
  "risk_type": "intent_mismatch",
  "embedding_model": "BAAI/bge-base-zh-v1.5",
  "embedding_similarity": 0.18,
  "reranker_model": "BAAI/bge-reranker-v2-m3",
  "reranker_score": 0.07,
  "decision_stage": "reranker",
  "reason": "user goal is summarize_mail but action is bank.transfer",
  "confidence": "high"
}
```

### 边界

1. 不要求训练专门模型。
2. 不要求做复杂向量数据库或检索系统。
3. 但必须实际引入 `BAAI/bge-base-zh-v1.5` 的 Embedding 编码与余弦相似度计算，不能只写规则判断。
4. 对高风险或灰区样本，必须实际接入 `BAAI/bge-reranker-v2-m3` 做二次复核，而不是只在文档中描述。
5. 不要求接入向量数据库；本项目核心目标是意图一致性判断，而不是大规模语义检索。
6. 风险判断必须输出结构化字段，不能只返回自然语言提示。
7. 阈值必须通过实验数据标定，不将开发阶段的固定经验值直接当作正式阈值。

### 交付标准

1. 能对高风险动作做一致性判定。
2. 能对提示注入和诱导操作给出明确阻断。
3. 能输出可展示、可审计的拦截理由。
4. 对 `state.update_memory`、`state.update_prompt` 等动作也能判定风险。
5. 至少能展示一组正常调用与恶意调用的相似度得分差异。

## 4.5 第二层 FISCO BCOS 身份与权限验证层

### 目标

在执行层对第一层漏过的调用做身份、签名和权限兜底。

### 具体实现方案

区块链底座固定采用 `FISCO BCOS`。

建议只做最小三类合约或等效链上数据结构：

1. `IdentityRegistry`
   记录 `DID -> public_key`
2. `PermissionRegistry`
   记录 `DID -> app/action -> allowed`
3. `AuditRegistry`
   记录关键审计摘要

网关接入链路必须固定为：

1. 本地生成 DID 和密钥对
2. 调用负载签名
3. 网关查链上公钥并验签
4. 网关查链上权限并验权
5. 验证通过后才允许执行
6. 执行摘要和拦截结果写链上审计

签名策略固定为：

1. 请求签名所用公钥必须与链上该 `DID` 注册公钥一致。
2. 不强行绑定某一种论文外的算法名词，只要求“注册公钥、请求签名、网关验签”三者完全一致。
3. 不默认复用 `OpenClaw` WebSocket 配对密钥作为业务请求签名密钥，除非该密钥已作为同一 `DID` 的合法注册公钥写链。

### 边界

1. 只把身份、公钥、权限、摘要放链上。
2. 不把全部业务明文上链。
3. 不把 `FISCO BCOS` 做成业务主系统，它只承担信任根和审计根作用。
4. 链交互失败时，`full` 模式下高风险动作默认拒绝，不允许降级放行。

### 交付标准

1. 至少有一个有效 DID 能成功完成签名调用。
2. 至少有一个越权动作会被链上权限拒绝。
3. 至少有一类关键结果能完成链上摘要写入。
4. 至少有一个链交互失败场景能被系统安全拒绝。

## 4.6 简易沙箱/受控执行层

### 目标

限制系统只能在受控边界内执行白名单动作，避免把整个课题做成“任意命令执行平台”。

### 具体实现方案

最终采用“进程内受控函数 + 白名单动作 + 参数限制”的简易沙箱方案。

必须体现：

1. `OpenClaw` 不可直接运行 shell。
2. 所有执行只能通过 `call_app_api` 进入。
3. App 只暴露预定义动作。
4. 对金额、文件路径、联系人等敏感参数做校验。
5. 对高风险动作强制经过防御链路。
6. 受保护状态写入不允许绕过沙箱与网关，直接触达文件。

### 边界

1. 不做 Docker/KVM/容器级重沙箱。
2. 不做完整移动操作系统模拟。
3. 不开放任意文件系统、任意网络、任意命令执行能力。

### 交付标准

1. 所有执行动作都能被枚举。
2. 没有一条执行链路可以跳过网关直接落到底层函数。
3. 高风险动作具备明确参数限制。
4. 受保护文件修改只能通过受控动作完成。

## 4.7 文件、记忆与关键配置完整性检测层

### 目标

满足老师特别强调的“文件检测与验证”要求，并覆盖共享提示词污染、记忆投毒和关键配置篡改。

### 具体实现方案

保留并整合：

1. [multiple-Agent/file_integrity_monitor.py](/home/chelizi/project/openq/prototypes/multiple-Agent/file_integrity_monitor.py)
2. [memory-p/file_integrity_monitor.py](/home/chelizi/project/openq/prototypes/memory-p/file_integrity_monitor.py)
3. [memory_refactor.py](/home/chelizi/project/openq/prototypes/memory-p/memory_refactor.py) 中的 diff 展示、人工确认、回滚思路

最终需要覆盖三类对象：

1. 共享提示词文件
2. 长期记忆文件
3. 关键配置文件

这些对象的修改在最终系统中统一抽象为：

1. `state.update_prompt`
2. `state.update_memory`
3. `state.update_config`

每类对象都至少要支持：

1. 哈希基线记录
2. 修改发现
3. 差异展示
4. 人工确认或自动阻断
5. 审计日志记录
6. `full` 模式下的人工确认或拒绝回滚

### 边界

1. 不需要做复杂文件系统级防病毒能力。
2. 不需要覆盖仓库里的所有文件。
3. 只覆盖与实验和系统安全直接相关的关键文件。
4. 对关键文件的正常变更与异常变更要能区分，不允许所有修改都一律阻断。

### 交付标准

1. 至少一个共享提示词污染场景可被检测。
2. 至少一个记忆投毒场景可触发人工确认或回滚。
3. 检测和处理结果可在页面和审计日志中展示。
4. 至少一个状态写入动作可走完整的“网关 -> 检测 -> 审批/回滚 -> 审计”链路。

## 4.8 审计与存证层

### 目标

对所有关键调用、拦截结果、执行结果提供可追溯记录。

### 具体实现方案

最终采用“本地结构化审计日志 + 链上摘要存证”双记录方案。

本地日志至少记录：

1. 时间戳
2. 会话 ID
3. DID
4. App
5. Action
6. 原始任务摘要
7. 风险判断结果
8. 验签验权结果
9. 最终执行结果
10. `request_id`
11. `resource_type`
12. 审批结果

链上只记录：

1. 请求摘要
2. 结果摘要
3. 拦截摘要
4. 时间戳

### 边界

1. 本地日志是完整记录。
2. 链上只做不可篡改证明。
3. 不追求复杂日志平台接入。
4. 审计字段必须在实验导出中可复用，避免日志格式和实验格式割裂。

### 交付标准

1. 每次高风险请求都能查到本地审计记录。
2. 至少一类关键记录可查到链上摘要。
3. 页面能展示一次调用的审计信息。
4. 页面能按 `request_id` 关联回复、拦截、执行和审计记录。

## 4.9 网站演示端

### 目标

满足老师“网站/管理端演示”的直观展示要求。

### 具体实现方案

建议用 `FastAPI + Jinja2` 做一个轻量网页，至少包含下面页面或面板：

1. **任务输入区**
   输入用户任务，选择运行模式
2. **调用链展示区**
   展示 OpenClaw 回复、网关调用、App 调用
3. **风险拦截区**
   展示第一层或第二层的拦截结果
4. **实验结果区**
   展示无防护、仅第一层、双层防护三种模式对比
5. **审计展示区**
   展示日志摘要、链上摘要
6. **状态变更展示区**
   展示共享提示词、记忆、配置的变更检测、审批和回滚结果

### 边界

1. 页面不追求复杂前端框架。
2. 页面主要承担展示职责，不承担复杂业务逻辑。
3. 只需足够支撑答辩和录屏演示。

### 交付标准

1. 能在网页中发起任务。
2. 能看到回复内容变化。
3. 能看到攻击被拦截或执行的结果差异。
4. 能看到审计信息和模式切换结果。
5. 能看到至少一个受保护状态修改场景的审批或回滚过程。

## 5. 三类实验的最终落地方案

## 5.1 实验一：提示注入与诱导操作

### 固定方案

1. 用户原始任务设为“总结邮件”。
2. `Mail_App` 返回一封带恶意指令的邮件。
3. 恶意内容诱导系统调用 `Bank_App.transfer`。
4. 第一层动态意图护栏必须识别“总结邮件”和“转账”不一致。

### 预期结果

1. `off`：错误调用可能发生
2. `guard_only`：大部分场景应被拦截
3. `full`：必须被拦截

## 5.2 实验二：跨 App 隐私窃取或越权调用

### 固定方案

1. 恶意外部内容诱导系统读取 `Gallery_App` 敏感资源，或执行未授权转账。
2. 即便第一层未完全拦住，第二层 `FISCO BCOS` 权限验证必须拒绝执行。

### 预期结果

1. `off`：存在越权成功可能
2. `guard_only`：可拦截一部分
3. `full`：真正落地执行必须失败

## 5.3 实验三：记忆投毒或关键状态篡改

### 固定方案

1. 模拟多轮对话、恶意升级或配置变更。
2. 目标对象为共享提示词、记忆文件、信任联系人或关键配置。
3. 完整性检测模块发现修改并展示 diff。
4. 无合法授权的修改必须被阻断、拒绝或回滚。

### 预期结果

1. `off`：关键状态可能被污染
2. `guard_only`：存在漏检风险
3. `full`：高危修改必须被阻断或触发人工确认

## 6. 消融实验与量化方案

### 目标

把系统直接做成可产出论文数据的状态，而不是后补实验。

### 固定模式

1. `off`
2. `guard_only`
3. `full`

### 固定统计指标

1. 攻击拦截率
2. 误报率
3. 平均响应延迟
4. 审计完整性说明
5. 状态篡改发现率
6. 意图一致性得分分布

### 目标结果

最终实现至少应逼近下面的目标：

1. 三类攻击总体拦截率达到或接近 95%
2. `full` 模式显著优于 `guard_only`
3. 误报率保持较低水平
4. 延迟开销处于可接受范围
5. 状态篡改检测对高危样本具备稳定发现能力

### 固定实现要求

1. 同一批攻击样本可在三种模式下重复运行。
2. 每个样本的结果都可结构化记录。
3. 能导出论文所需表格或图表原始数据。

实验导出建议至少包含下面字段：

1. `sample_id`
2. `scenario_type`
3. `mode`
4. `request_id`
5. `expected_result`
6. `actual_result`
7. `blocked_layer`
8. `latency_ms`
9. `false_positive`
10. `audit_written`
11. `intent_similarity`

### 交付标准

1. 三种模式均可运行。
2. 三类实验均可在三种模式下对比。
3. 至少能产出一套用于论文的统计表。
4. 导出结果能直接支撑第五章和第六章中的表格整理。

## 9. 交付程度定义

为了避免“做了一半但说不清是否完成”，最终交付程度按下面标准定义。

## 9.1 可接受交付

满足下面条件，即可视为达到课题答辩级交付：

1. 系统主链路可跑通
2. 三个核心 App 可用
3. 三类实验可演示
4. 三种模式可切换
5. 第一层和第二层都真实存在
6. 文件检测与记忆检测可演示
7. 网页端可展示回复变化、拦截结果、审计结果
8. 受保护状态写入走统一协议，不再靠独立脚本直接改文件

## 9.2 较好交付

在“可接受交付”基础上，再满足：

1. 三类实验有较完整样本集
2. 统计结果可直接写入论文
3. 页面可展示更完整调用链
4. 链上审计和本地审计关联更完整
5. 数据导出可直接生成论文表格

## 9.3 不算完成的情况

下面任何一种都不应视为最终完成：

1. 只有原型脚本，没有统一系统
2. 只有网页，没有真实双层防御
3. 只有文档，没有可跑的实验
4. 只有文件检测，没有链上验证
5. 只有链上验证，没有网页演示和实验对比
6. App 调用和状态写入走两套不同安全链路

## 9.4 最终验收场景

最终交付前，至少要能稳定复现下面 5 个验收场景：

1. 正常邮件总结场景
   系统能正常读取邮件并返回总结，不触发错误拦截
2. 恶意邮件诱导转账场景
   `guard_only` 和 `full` 能明确给出阻断结果
3. 跨 App 隐私读取或越权转账场景
   `full` 模式必须在第二层拒绝执行
4. 共享提示词或记忆污染场景
   系统能展示 diff、审批或回滚结果
5. 审计与网页联动场景
   页面能按 `request_id` 展示一次完整调用的回复、拦截、执行、审计和链上摘要
