# OpenQ 课题最终定位与交付路线图

## 1. 文档目的

本文档回答五个问题：

1. 这个课题现在到底在做什么。
2. 这个课题真正的核心功能是什么。
3. 理想的最终版本应该长成什么样。
4. 现有代码距离理想最终版还差哪些关键能力。
5. 后续应该按什么顺序推进，做到什么程度算可以交付。

本文档不是代码设计文档，也不是单次开发 TODO，而是面向最终版本收敛的判断基准。

## 2. 课题的本质定义

### 2.1 不是在做什么

这个课题最终不是：

1. 一个单纯的 OpenClaw 管理网站。
2. 几个零散攻击 demo 的拼接。
3. 一个只靠规则拦截的网页安全演示。
4. 一个只强调区块链接入、但和智能体调用链脱节的系统。

### 2.2 真正在做什么

这个课题本质上是在做一套：

**面向 AI 智能体的虚拟终端多 App 安全防护系统**

其核心叙事应该固定为：

1. OpenClaw 作为跨 App 智能体生成结构化调用计划。
2. 所有调用统一进入受控网关。
3. 第一层语义意图护栏判断是否发生任务偏移。
4. 第二层 FISCO BCOS 验签验权判断调用是否合法。
5. 通过校验后，调用才进入虚拟 App 或受保护状态。
6. 本地审计、链上摘要、前端可视化共同形成证据闭环。

这个系统要证明的不是“系统能运行”，而是：

1. AI 智能体在多 App 场景下确实会受到提示注入、越权诱导、记忆污染等攻击影响。
2. 单层防御不够稳。
3. 双层协同防御比无防御和单层防御更有效。

## 3. 当前系统的功能拆解

结合现有代码，当前系统已经具备的功能可以归纳为五个层面。

### 3.1 智能体规划与调度

当前系统已经具备：

1. OpenClaw WebSocket 连接能力。
2. 结构化计划解析能力。
3. 调试 planner 和真实 planner 双路径。
4. 统一编排器对 scenario、mode、request trace 的调度能力。

对应主实现集中在：

1. `app/core/openclaw.py`
2. `app/core/experiments.py`

### 3.2 统一调用网关

当前系统已经具备：

1. 所有 App/state 调用统一协议化。
2. 统一参数验证。
3. 网关内串联 guard、chain、dispatcher、audit。
4. 统一结构化响应和审计记录。

对应主实现集中在：

1. `app/core/gateway.py`
2. `app/core/request_builder.py`
3. `app/core/actions.py`

### 3.3 虚拟终端与受保护状态

当前系统已经具备：

1. `mail / bank / gallery / weather` 虚拟 App。
2. `memory / prompt / config` 等受保护状态目标。
3. 审批、回滚、完整性检测的基本能力。

对应主实现集中在：

1. `app/apps/services.py`
2. `app/state/store.py`
3. `app/state/approval.py`

### 3.4 双层防御与信任根

当前系统已经具备：

1. embedding + reranker 驱动的意图护栏。
2. FISCO BCOS 验签验权。
3. 本地审计与链上审计摘要。
4. 链不可用时的有限降级策略。

对应主实现集中在：

1. `app/guards/intent.py`
2. `app/chain/fisco.py`
3. `app/audit/service.py`

### 3.5 可视化演示与实验

当前系统已经具备：

1. 单页面演示控制台。
2. 三模式运行。
3. 统一日志和实时事件流。
4. 批量实验和结果导出。

对应主实现集中在：

1. `app/api/routes.py`
2. `app/demo/templates/index.html`
3. `app/core/realtime.py`

## 4. 这个课题真正的核心功能

从论文和演示视角看，真正的核心功能只有两个。

### 4.1 核心功能一：真实的智能体受控调用链

必须证明：

1. 用户任务不是直接走固定脚本。
2. OpenClaw 真实地产生结构化调用计划。
3. 这个计划进入统一网关后再经过双层防御与执行。
4. 系统不会在背后偷偷把 OpenClaw 的结果改回预设答案。

如果这一点不成立，课题就会退化成“预设剧本 + 网关演示”。

### 4.2 核心功能二：双层防御有效性证明

必须证明：

1. `off` 模式下攻击容易成功。
2. `guard_only` 能拦住一部分语义攻击，但不是全部。
3. `full` 才是完整防护链路。
4. 正常任务不能因为防御开启而大面积误杀。

如果这一点不成立，系统再完整，也很难支撑论文结论。

## 5. 理想的最终版本应该长成什么样

### 5.1 从系统结构上看

理想的最终版应该是一套单一主工程，而不是多套原型并行：

1. 一个统一的主服务。
2. 一个统一的前端演示入口。
3. 一套统一的数据结构和调用协议。
4. 一组固定的实验场景与导出结果。

### 5.2 从演示效果上看

理想的最终版页面应该让老师在不看代码的情况下，也能快速理解：

1. 用户输入了什么。
2. OpenClaw 规划了什么。
3. 调用经过了哪些防线。
4. 最终在哪一层被拦下或执行成功。
5. 审计和链上证据在哪里。
6. 三种模式为什么会出现不同结果。

### 5.3 从论文支撑上看

理想的最终版应该能直接支撑第五章和第六章：

1. 系统结构图可以直接从实现抽象出来。
2. 关键链路可以直接截图和说明。
3. 实验数据能直接导出并画图。
4. 典型案例能同时展示攻击成功和防御成功两种效果。

## 6. 现有代码距离理想最终版还差什么

下面不是泛泛而谈，而是按“是否影响最终交付”排序后的缺口。

### 6.1 课题叙事层缺口

这是最重要的一层，因为它决定系统是否“像一个完整课题”。

当前缺口：

1. 前端虽然能看结果，但“故事线”还不够明确。
2. 用户看到的是很多底层字段和技术细节，但不一定第一眼就明白本次实验想证明什么。
3. 页面更像控制台，而不是“实验展示台 + 证据台 + 结论台”三者合一。

这会导致两个问题：

1. 演示时需要你口头解释很多内容。
2. 系统结论不够“自动显现”。

### 6.2 研究可信度层缺口

当前实现已经比早期版本真实很多，但还差几件能显著提升可信度的东西：

1. 缺少一个明确的“真实 OpenClaw 模式 / 调试模式”前端标识。
2. 缺少对规划质量的显式展示，例如计划是否命中 oracle、是否偏离任务目标。
3. 批量实验默认走真实 OpenClaw，虽然更真，但容易引入不稳定性，论文导出与现场复现之间仍存在张力。

这里的核心矛盾是：

1. 演示需要稳定。
2. 课题又需要真实性。

最终版需要把“研究真实性”和“现场可控性”分成两个清晰的运行档位，而不是混在一个按钮里。

### 6.3 前端展示层缺口

当前前端功能已经够多，但展示逻辑仍然偏“工程控制台”，还不够“课题终稿”。

主要问题：

1. 首页信息密度太高，第一次看会分不清主次。
2. 场景、执行链、日志、实验、审批、状态工具都放在同一页，专家理解没问题，但老师第一次看可能抓不住重点。
3. 当前日志已经统一了，但仍偏向技术日志，不够像“证据时间线”。
4. 页面缺少一块非常明确的“本次请求的最终结论卡片”。
5. 缺少“攻击前 / 攻击后 / 防御后”的对照视图。
6. 三模式对比是有的，但视觉权重还不够高，不像课题亮点。

### 6.4 实验层缺口

当前实验能力已经具备，但从论文角度还可以再收紧：

1. 需要把实验样本数和场景类别再明确成固定基线。
2. 需要区分“论文基准实验”和“现场自由演示”。
3. 需要更明确的导出清单，例如：
   - 总结果 JSON
   - 每样本 trace
   - 每模式统计 CSV
   - 典型案例截图

否则最后会出现“系统能跑，但整理论文证据仍然临时手工拼”。

### 6.5 可运维交付层缺口

一个能交付的毕设系统，不只是代码能启动，还要具备：

1. 一键启动。
2. 一键预检查。
3. 一键跑 demo。
4. 一键导出实验结果。
5. 明确的演示脚本。

当前脚本已经在补，但还缺少“最后演示操作手册”的统一整理。

## 7. 前端还需要怎么调整，才能更好展示

前端不是缺功能，而是缺“展示收敛”。

### 7.1 首页需要更像实验舞台

建议把首页的主要展示目标压成三个区块：

1. **输入与场景**
   用户任务、场景说明、攻击类型、当前模式、是否真实 OpenClaw。

2. **执行与阻断**
   OpenClaw 规划、网关链路、最终结果、阻断层。

3. **证据与对比**
   审计记录、链上存证、三模式对比、状态 diff。

当前这些内容都有，但权重比较平均，导致“能看懂”但“不够聚焦”。

### 7.2 需要一个更强的“结论区”

建议前端新增一个非常醒目的最终结论面板，固定显示：

1. 当前是正常任务还是攻击任务。
2. 最终状态是执行成功还是被阻断。
3. 被哪一层阻断。
4. 这次结果是否符合预期。
5. 本次能证明什么结论。

这个区域应该是整页视觉中心，而不是藏在当前日志和右侧状态块里。

### 7.3 三模式对比需要升格为首页亮点

当前三模式对比是存在的，但更像附属信息。

最终版里，三模式对比应该成为课题亮点之一。建议：

1. 用固定三列卡片展示 `off / guard_only / full`。
2. 每列统一显示：
   - final_status
   - blocked_layer
   - execution_result
   - 审计状态
3. 加一句自动生成的差异总结，例如：
   `off 成功越权，guard_only 阻断提示注入，full 阻断越权执行`

### 7.4 日志区要从“技术日志”升级为“证据时间线”

建议统一日志面板增加切换：

1. `摘要视图`
   只显示关键节点：规划、guard、chain、execute、audit。

2. `原始视图`
   保留现有完整统一日志。

这样老师看摘要，答辩追问时再切原始证据，会更自然。

### 7.5 需要明确“真实模式”和“演示模式”

当前前端有 `连接真实大模型` 复选框，但语义不够强。

建议改成更明确的两档：

1. `真实 OpenClaw 模式`
   用于证明系统真实性，失败即失败。

2. `演示复放模式`
   用于稳定展示论文中的固定案例。

这是最终版非常重要的展示边界。

## 8. 我认为最理想的最终交付形态

最终交付不应该只是“给老师看网页”，而应该是一个完整交付包。

### 8.1 最小完整交付包

至少包含：

1. 可运行系统仓库。
2. 启动与部署脚本。
3. 演示手册。
4. 论文实验导出数据。
5. 典型案例截图或录屏。
6. 系统结构说明文档。

### 8.2 最理想的交付展示流程

我认为最理想的最终答辩展示流程应该固定为：

1. 用一个正常场景证明系统不是“一开防御就全拦”。
2. 用一个提示注入场景展示 `guard_only` 的价值。
3. 用一个跨 App 越权场景展示 `full` 的价值。
4. 用一个记忆或共享提示词篡改场景展示状态保护、审批与回滚。
5. 最后用批量实验结果给出整体结论。

这样展示的叙事是最完整的。

## 9. 什么效果下我认为可以交付

下面五条同时成立时，我认为系统已经达到“可交付的最终版”。

### 9.1 系统链路闭环

真实 OpenClaw、网关、guard、chain、虚拟 App/state、audit、前端展示已经形成稳定闭环。

### 9.2 正常与攻击样本都成立

1. 正常任务能通过。
2. 攻击任务能在合适层拦截。
3. 结果可重复，不是靠运气。

### 9.3 三模式差异稳定且可解释

1. `off` 最脆弱。
2. `guard_only` 展示单层效果。
3. `full` 展示完整效果。

并且这种差异能通过前端直接看出来。

### 9.4 页面已经具备答辩展示质量

1. 不是纯开发控制台。
2. 不是只靠你口头解释才能明白。
3. 页面本身就能把“发生了什么、为什么、结论是什么”表达清楚。

### 9.5 论文证据已可直接复用

1. 结构图能抽出来。
2. 案例图能截出来。
3. 实验数据能导出来。
4. 结论能由数据直接支撑。

## 10. 建议的收敛计划

下面的计划不是“无限开发清单”，而是面向最后交付的收敛路线。

### 10.1 第一优先级：把页面从“控制台”收敛成“答辩展示页”

目标：

1. 新增结论区。
2. 强化三模式对比区。
3. 区分摘要证据和原始日志。
4. 明确真实模式 / 演示模式。

这是最该优先补的，因为它直接影响最后展示质量。

### 10.2 第二优先级：把实验体系从“可跑”收敛成“论文基线”

目标：

1. 固定最终场景集。
2. 固定论文基准实验口径。
3. 固定导出格式和结果目录。
4. 固定哪些图和表可以直接进论文。

### 10.3 第三优先级：把运行方式从“开发态”收敛成“交付态”

目标：

1. 一键启动。
2. 一键健康检查。
3. 一键跑固定 demo。
4. 一键导出实验。
5. 一份简短但可靠的演示手册。

### 10.4 第四优先级：继续补真实性和稳定性的边界说明

目标：

1. 前端清楚标注当前是 `真实 OpenClaw` 还是 `演示复放`。
2. 导出结果中明确记录 planner backend。
3. 让“真实性”和“可控性”的边界在系统里可见，而不是只在口头解释中存在。

## 11. 最终结论

当前系统已经不再是早期原型，而是已经具备了最终课题的主骨架。

它现在最缺的不是更多功能，而是最后一轮“收敛”：

1. 收敛成更清晰的课题叙事。
2. 收敛成更强的前端展示逻辑。
3. 收敛成更固定的实验口径。
4. 收敛成更像最终交付物的运行与导出方式。

后续如果继续开发，优先级不应该是“继续堆模块”，而应该是：

**围绕最终答辩、最终论文、最终交付去做最后一轮产品化和证据化收敛。**
