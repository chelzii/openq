# OpenQ 深度 Review 与最终收敛计划

## 1. 文档目的

本文件基于以下内容交叉审查后形成：

1. `docs/xuqiu/xuqiu.md`
2. `docs/最终版需求文档.md`
3. `docs/最终版实现文档.md`
4. 当前主工程 `app/`、`data/`、`tests/`
5. `prototypes/multiple-Agent` 与 `prototypes/memory-p` 中已被最终文档点名应吸收的能力

目标不是重复描述“系统应该做什么”，而是明确：

1. 当前仓库已经做到什么程度
2. 哪些地方只是初步实现，离“良好实现”还有差距
3. 哪些要求尚未真正落地
4. 接下来应按什么顺序收敛，才能达到课题最终交付标准

---

## 2. 总体判断

### 2.1 当前项目的优点

当前仓库已经完成了最终方案的主骨架，方向基本正确，主要体现在：

1. 已收敛为单一主工程，而不是继续分散在多个原型目录
2. 已具备虚拟 App、统一网关、三种运行模式、实验导出、网页演示入口
3. 第一层意图护栏已经切换到真实模型链路，使用 `BAAI/bge-base-zh-v1.5` + `BAAI/bge-reranker-v2-m3`
4. 已有受保护状态、diff、审批、审计、链状态展示等基础能力
5. 已有基础测试集，能覆盖正常样本、提示注入、越权、记忆投毒、提示词污染等主场景

### 2.2 当前项目的总体结论

如果标准是“已经有一版可跑演示系统”，当前仓库已经达标。  
如果标准是“已经良好按照课题最终需求实现，可以作为最终版交付”，我当前结论是：

**还没有完全收口，仍处于“主结构已成，但关键链路存在演示化/替代式实现”的阶段。**

最主要的问题不是“没有代码”，而是以下几条核心链路还没有达到最终文档要求的真实性、统一性和闭环程度：

1. 第二层区块链验证仍不是实际信任根
2. OpenClaw 还没有真正生成结构化调用并驱动网关
3. 受保护状态写入还存在绕过统一协议的捷径
4. 简易沙箱具备雏形，但还没有形成更完整的受控执行约束体系
5. 演示端和实验端还不足以充分支撑“答辩展示 + 论文数据”

---

## 3. 需求对照结论

### 3.1 已基本实现的部分

以下能力可以认为“已经有较完整基础”：

1. 单一主工程结构
2. 虚拟 App 生态的基础版本
3. 统一调用网关入口
4. 三种模式 `off / guard_only / full`
5. 第一层语义护栏模型化实现
6. 受保护状态的哈希基线、diff、审批、回滚入口
7. 本地结构化审计日志
8. 网页演示入口
9. 三类实验样本的最小闭环

### 3.2 只做到了“初步实现”的部分

以下部分方向对了，但实现深度还不够：

1. `FISCO BCOS` 接入
2. OpenClaw 接入层
3. 简易沙箱
4. 文件/记忆/提示词完整性检测
5. 审计与链上存证
6. 演示前端
7. 实验统计与论文数据支撑

### 3.3 尚未真正完成的部分

以下内容仍不能按“最终版已完成”来判断：

1. 真正基于链上注册信息的 DID、公钥、权限、审计闭环
2. OpenClaw 真实结构化工具调用到网关的闭环
3. 所有受保护动作统一走同一协议，没有旁路
4. 更严谨的沙箱白名单与参数策略
5. 面向答辩的攻击前后差异可视化
6. 面向论文的更系统实验样本、失败场景和统计说明

---

## 4. 深度 Review 发现

以下问题按优先级排序。

### 4.1 P0: 第二层区块链验证仍是“链活性探测 + 本地注册表”

当前 `FiscoBcosService` 会探测端口和块高，但真正的身份、公钥、权限、审计记录仍主要依赖本地 `ledger.json`。  
这意味着第二层目前并没有真正承担最终文档要求的“身份与权限信任根”职责。

当前表现：

1. `authorize()` 读取本地 `identities` 和 `permissions`
2. `record_audit()` 只是把摘要追加到本地 `audit_registry`
3. 链的存在更多用于“证明节点在线”，不是“验证请求是否合法”

影响：

1. 不满足“链上公钥校验、链上权限查询、链上审计存证”的最终要求
2. `full` 模式的安全语义仍不够强
3. 无法严谨支撑论文中“第二层兜底”的论证

结论：

**这是当前仓库距离“最终版良好实现”最大的缺口。**

### 4.2 P0: OpenClaw 还没有真正生成结构化调用请求

当前 `OpenClawFacade` 主要负责返回一段文本回复。  
真正的 `app/action/args` 来自 `data/fixtures/scenarios.json` 中预定义的 `steps`，由 `DemoOrchestrator` 直接拼出 `CallAppRequest`。

影响：

1. 当前请求链路不是“用户任务 -> OpenClaw -> 结构化工具调用 -> 网关”
2. 而是“用户任务 -> 场景 fixture -> 网关”
3. 这会削弱最终方案里“OpenClaw 是被保护对象和调度入口”的真实性

结论：

**当前系统更像“带 OpenClaw 文本回复的网关演示器”，还不是“OpenClaw 驱动的正式系统”。**

### 4.3 P0: 受保护状态写入仍有旁路，服务端替调用者代签

`/api/state/update` 当前会在服务端直接读取 demo identity 的私钥并生成签名。  
这与最终实现文档中“所有受保护动作都纳入统一协议，不存在第二套旁路执行逻辑”的要求不一致。

影响：

1. 服务端代签会掩盖真实调用者身份
2. 无法体现“无合法签名的高危修改必须被拒绝”
3. 受保护状态与普通 App 调用仍没有完全统一到一条执行协议

结论：

**必须把这条路径收口成真正的统一调用协议，不能继续保留演示捷径。**

### 4.4 P1: 简易沙箱已有基础，但还不够“制度化”

当前系统已经具备：

1. 白名单 App
2. 白名单 Action
3. 不开放任意 shell
4. 不开放任意文件系统与任意网络转发

这说明“简易沙箱/等效受控执行环境”已经有基础。  
但当前仍偏向“进程内函数分发器”，没有进一步形成更明确的执行边界制度。

不足体现在：

1. 动作清单分散在 `if/elif` 分发逻辑里，不利于统一治理
2. 参数约束还不够系统化，主要只对部分高风险动作做了显式限制
3. 缺少按动作级别定义的风险等级、参数 schema、审批策略、额度策略
4. 缺少统一拒绝策略，例如链失败时哪些动作 fail-closed、哪些动作允许低风险降级

结论：

**沙箱不是完全没做，但还没有达到“写到论文里也足够稳”的程度。**

### 4.5 P1: 文件完整性检测已经有 diff 和审批，但仍偏静态规则化

当前已经覆盖了记忆、共享提示词、配置三类对象，也有：

1. 哈希基线
2. unified diff
3. 风险标签
4. 审批/阻断
5. 回滚标记

但与最终文档和原型能力相比，仍有几个缺口：

1. 当前主要依赖字符串模式匹配，缺少更稳定的风险判定策略
2. 缺少后台持续监视或调用前后快照核验的完整机制
3. `rollback()` 只是设置标记，没有明确恢复基线快照的机制
4. 缺少“正常变更”和“恶意变更”的更细粒度判别依据

结论：

**现在能挡住样例，但还不够支撑“良好的文件检测与验证系统”这一表述。**

### 4.6 P1: 演示端仍偏 JSON 控制台，不足以支撑最终答辩展示

当前页面能跑流程，但主要还是把结果直接 `JSON.stringify` 输出。  
这对于开发调试够用，但离“正式演示端”还有距离。

缺口主要包括：

1. 没有突出展示“攻击前后 OpenClaw 回复差异”
2. 没有清晰分层展示“第一层拦截 / 第二层拒绝 / 状态审批阻断”
3. 没有直观呈现调用链、关键参数和审计关联
4. 没有把实验结果整理成便于论文截图和答辩讲解的视图

结论：

**演示端目前是工程调试台，不是高完成度展示层。**

### 4.7 P1: 实验样本和统计还不够“论文化”

当前已有样本和导出，但还偏最小集。  
如果目标是“良好实现 + 论文可直接复用”，还应继续补强：

1. 样本规模偏小
2. 正常样本覆盖不足，不利于支撑误报率分析
3. 缺少链失效、签名非法、权限缺失、审批拒绝等负向验证样本
4. 缺少更完整的意图相似度分布、混淆分析、案例归档

结论：

**当前实验更像功能回归，不是完整实验方案。**

### 4.8 P2: 测试覆盖还没有深入到“最终版关键风险”

现有测试已经覆盖主流程，但还缺少以下关键断言：

1. 非法签名必须失败
2. 篡改 `payload_hash` 必须失败
3. 链不可用时 `full` 模式高风险动作必须 fail-closed
4. 不同 DID 的权限边界必须被验证
5. 状态回滚后的基线一致性必须被验证
6. OpenClaw 真实结构化输出解析失败时的系统行为必须被验证

结论：

**当前测试能证明“系统能跑”，但还不足以证明“关键边界是稳的”。**

---

## 5. 收敛目标

后续实现不应继续以“再补一个功能点”为思路，而应以以下最终标准为目标：

1. 所有动作统一走同一条结构化受控调用协议
2. OpenClaw 真正成为结构化调用的生成入口
3. 第二层验证真正依赖链上身份、公钥、权限与审计
4. 高风险动作在链失败、签名非法、权限缺失时必须稳定拒绝
5. 受保护状态具备真实的检测、审批、回滚和审计闭环
6. 演示端能直观展示“回复变化、拦截层次、执行结果、审计关联”
7. 实验与测试能直接支撑论文第五章和第六章

---

## 6. 详细整改计划

## 阶段 0：冻结最终协议与验收口径

### 目标

先把最终实现边界冻结，避免后续继续出现“演示用捷径”和“正式链路”并存。

### 任务

1. 固化 `call_app_api` 协议字段，明确 `did / payload_hash / signature / context / metadata`
2. 明确 `resource_type=app` 与 `resource_type=state` 完全复用同一协议
3. 明确哪些动作属于高风险动作，以及对应的 fail-closed 策略
4. 明确哪些场景属于论文正式样本，哪些属于调试样本

### 交付物

1. 协议说明文档
2. 风险动作清单
3. 模式行为矩阵

### 验收标准

1. 系统不存在第二套执行协议
2. 每个动作都能说清楚“走哪些防线、失败时如何处理”

## 阶段 1：重构第二层为真实链上信任根

### 目标

让 `FISCO BCOS` 真正承担 DID、公钥、权限、审计四项职责，而不是只做在线探测。

### 任务

1. 设计最小合约或等效链上数据结构：
   - `IdentityRegistry`
   - `PermissionRegistry`
   - `AuditRegistry`
2. 用 Python 后端接入实际链查询与写入
3. 将 `authorize()` 改为：
   - 查链上 DID 是否存在
   - 查链上公钥
   - 验签
   - 查链上权限
4. 将 `record_audit()` 改为真实上链写摘要
5. 保留本地镜像作为缓存或演示兜底，但不能再作为 `full` 模式的主判定来源
6. 明确链不可用时的处理：
   - 高风险动作拒绝
   - 普通低风险动作是否允许降级要写清楚

### 交付物

1. 实际可调用的链注册/查询/审计接口
2. 一组初始化脚本，用于注册 DID、公钥、权限
3. 链交互错误码与网关错误语义

### 验收标准

1. 至少一个合法 DID 能通过完整验签验权
2. 至少一个越权动作能被链上权限拒绝
3. 至少一条审计摘要能被真实写入链上
4. 链断开时 `full` 模式高风险动作默认拒绝

## 阶段 2：让 OpenClaw 真正生成结构化调用

### 目标

把当前“fixture steps 驱动执行”收敛为“OpenClaw 输出结构化意图，再由网关执行”。

### 任务

1. 明确 OpenClaw 的结构化输出格式
2. 为 OpenClaw 设计统一工具描述，只允许输出 `call_app_api`
3. 增加结构化输出解析、校验、重试与降级逻辑
4. 保留 fixture，但仅用于：
   - 回归测试
   - 离线实验重放
   - 对照组输入
5. 页面展示中区分：
   - OpenClaw 原始回复
   - 结构化工具调用
   - 网关执行结果

### 交付物

1. OpenClaw 结构化调用适配层
2. 工具调用 schema
3. 解析失败与回退策略

### 验收标准

1. 用户任务能通过 OpenClaw 生成结构化调用
2. 网页能展示完整的“任务 -> 回复 -> 调用 -> 执行”链路
3. fixture 不再承担正式主链路执行职责

## 阶段 3：彻底统一受保护状态写入协议

### 目标

取消服务端代签和旁路写入，让状态写入与普通 App 调用完全统一。

### 任务

1. 删除 `/api/state/update` 中的服务端代签逻辑
2. 将状态修改改为真正的 `CallAppRequest`
3. 对 `state.update_memory / update_prompt / update_config` 明确动作级权限
4. 将审批结果也纳入同一审计模型
5. 增加“审批通过后重新提交签名请求”或“审批令牌绑定 request_id”的机制

### 交付物

1. 统一状态修改协议
2. 审批令牌设计
3. 审批与执行关联审计

### 验收标准

1. 不存在服务端替调用者代签
2. 状态修改动作与 App 动作共享同一网关逻辑
3. 无签名或无审批的高危状态修改稳定失败

## 阶段 4：增强简易沙箱与执行治理

### 目标

把当前函数式分发器升级为更制度化的受控执行层。

### 任务

1. 建立统一动作注册表，而不是散落在 `if/elif`
2. 为每个动作定义：
   - 参数 schema
   - 风险级别
   - 权限 key
   - 是否需要审批
   - 额度/路径/对象白名单
3. 为高风险动作增加更强参数约束：
   - 转账金额
   - 目标账户白名单/黑名单
   - 相册资产可见范围
   - 状态文件允许修改的目标范围
4. 把“链失败时拒绝”“审批缺失时拒绝”“参数异常时拒绝”都固化为统一策略

### 交付物

1. 动作注册表
2. 统一执行策略表
3. 风险分级说明

### 验收标准

1. 所有可执行动作都可枚举
2. 任意动作都能追溯其校验规则
3. 不存在未登记动作直接落到底层函数

## 阶段 5：把文件检测与状态保护做完整

### 目标

让“文件检测与验证”真正达到课题要求，而不是只靠几个风险词挡样例。

### 任务

1. 引入基线快照恢复能力，回滚应真正恢复文件内容
2. 增加调用前/调用后快照核验
3. 结合 diff、风险标签、目标类型，细化审批策略
4. 对正常修改建立白名单样本，降低误报
5. 视需要补充后台监测线程或按需扫描能力
6. 让本地日志、页面展示、链上摘要三者保持同一 `request_id`

### 交付物

1. 真正可恢复的回滚机制
2. 更细粒度的状态风险分类
3. 审批策略矩阵

### 验收标准

1. 至少一个记忆投毒样例能真实回滚到基线
2. 至少一个共享提示词正常修改可在审批后通过
3. 页面和审计中能看到 diff、风险标签、审批和回滚结果

## 阶段 6：重做演示端为正式展示层

### 目标

把当前调试页升级成真正适合答辩的演示面板。

### 任务

1. 重构页面信息布局，分为：
   - 任务与模式
   - OpenClaw 回复
   - 结构化调用链
   - 第一层防御结果
   - 第二层链验证结果
   - 状态修改/审批/回滚
   - 审计与链摘要
2. 增加“攻击前/攻击后/防御后”的对比视图
3. 增加实验统计卡片，而不是原始 JSON
4. 增加 `request_id` 关联视图，便于展示一次调用的全过程

### 交付物

1. 正式演示页面
2. 对比视图
3. 审计联动视图

### 验收标准

1. 页面能直观看到回复内容变化
2. 页面能看出到底是哪个防线拦截了请求
3. 页面能直接用于答辩录屏，不需要开发者再解释大量 JSON

## 阶段 7：补齐实验设计到论文可用程度

### 目标

把当前实验从“功能样例集”提升为“论文实验集”。

### 任务

1. 扩展 benign 样本，覆盖更多正常任务
2. 扩展恶意样本，覆盖：
   - 显式提示注入
   - 隐式诱导
   - 跨 App 越权
   - 非法签名
   - 权限缺失
   - 链失效
   - 共享提示词污染
   - 记忆投毒
   - 配置篡改

## 7. 推荐实施顺序

为避免反复返工，建议严格按下面顺序实施：

1. 先做阶段 0，冻结协议和验收口径
2. 再做阶段 1，先把第二层真正落地
